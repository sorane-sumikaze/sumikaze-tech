# sumikaze.tech

宙音 / Sorane の個人サイト兼、実装の実験場。

https://sumikaze.tech

## 構成

素の HTML / CSS / JavaScript。ビルド工程を持たない。
GitHub Pages（`main` ブランチ直下）から配信している。

| ファイル | 内容 |
|---|---|
| `index.html` | トップページ |
| `method.html` | AI を前提とした開発プロセスの方法論 |

CSS は各ファイルにインラインで保持している。共通化はファイルが3枚目に達した時点で再検討する。2枚の段階で共通の CSS ファイルを1本増やすことは、重複が消える代わりにリクエストが1本増えるトレードオフであり、判断材料が足りない。

## URL の規約

- 単発の固定ページは apex 直下に置く（例：`/method.html`）
- ブログ記事は `/blog/` 以下の名前空間を予約している（未実装）

単発ページを apex 直下に固定することで、記事の URL 構造が未決のままでも固定ページを追加できる。

## 変更管理

### Issue を起票してから着手する

このリポジトリへの変更は、原則として Issue を立ててから行う。

URL 設計や掲載基準のように、**コミットメッセージでは表現できない判断が繰り返し発生する**ため。検討して却下した選択肢とその理由が残らなければ、同じ検討を将来やり直すことになる。

### Pull Request は当面使わない

GitHub Pages にはデプロイプレビューが存在しない。Actions を組まない限り、PR を立てても `main` へマージするまで実際の表示を確認できない。品質保証として機能せず、レビュアーが1人である以上は承認プロセスとしても形骸化する。

効果を確認できない工程を先に導入しない、という判断による。

以下のいずれかを満たした時点で PR 運用へ移行する。

- Actions によるビルドまたはリンクチェックを導入したとき
- 自分以外がコミットする状況が発生したとき

それまでは `main` への直接コミットを維持する。
